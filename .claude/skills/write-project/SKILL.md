# Write a project write-up

You are producing one page of Abi's portfolio: `src/content/projects/<slug>/index.md`
(plus an optional `case-study.md`). It must read as if Abi wrote it, matching the
hand-written write-ups already on the site. It should not read like documentation
generated from code.

Read these before doing anything else. They are the whole specification:

1. `style-guide.md` (next to this file): voice, abstraction level, structure, and what to leave out.
2. `format.md`: the Markdown blocks the site renders. Anything else fails the build.
3. The reference write-ups. Read all four in full, because they define the house style better than any rule:
   - `src/content/projects/third-party-services-framework/index.md`: a framework explained through its components
   - `src/content/projects/data-upload/index.md`: a feature with an Overview + Deep Dive
   - `src/content/projects/legal-hold-notifications/index.md`: a product with separate modules (the most sections any page has)
   - `src/content/projects/google-vault-collector/index.md`: an integration, linking to the framework it builds on

Do **not** use PropMange (`src/projects/PropMange.tsx`) or Chip8 (`src/projects/Chip8Emulator.tsx`)
as references. They are earlier AI-generated pages in the wrong register and are due to be
regenerated by this skill. `style-guide.md` quotes them as counterexamples.

## The pipeline

Work through these steps in order. **Steps 2 and 5 end by waiting for the user.** Don't
continue past them in the same turn.

### 1. Gather inputs

- The project's source: a GitHub URL (the usual case), a local path, or nothing. Take it
  from the arguments, or ask. Work projects may have no accessible code, in which case
  the brief is the only source, and that's fine.
- **A GitHub URL is cloned into a temporary folder** for the duration of the run. This
  session runs in a devcontainer where only this repo is mounted, so cloning is how other
  projects get in:

  ```bash
  GIT_TERMINAL_PROMPT=0 timeout 120 \
    git clone --filter=blob:none <url> "${TMPDIR:-/tmp}/write-project/<slug>"
  ```

  `--filter=blob:none` skips old file versions but keeps the full commit history, which
  step 3 uses for the years. Public repos clone over HTTPS with no credentials.
  `GIT_TERMINAL_PROMPT=0` and the timeout make a private repo fail fast instead of
  waiting on a credentials prompt that can't be answered from here (an SSH URL can stall
  the same way on a passphrase or host-key prompt). When that happens, ask the user to
  run the clone themselves with the `!` prefix, then carry on from that folder:

  ```bash
  ! git clone --filter=blob:none <url> "${TMPDIR:-/tmp}/write-project/<slug>"
  ```

- Treat the clone as read-only: read it, never modify, build or commit to it.
- A local path is used as-is, which only works if it's visible inside this container.
- If `src/content/projects/<slug>/brief.md` already exists, this is a regeneration.
  Read the brief and the current write-up, and skip to step 3. In step 2, ask only what's
  changed.

### 2. Ask the core questionnaire

Ask every question in `questionnaire.md` (Part 1) in **one message** as a numbered list,
so the user can answer in one reply. Ask before you read the code. The answers decide what
the code reading should look for. Then stop and wait.

### 3. Analyze the project

Read for the shape of the system, not its details:

- README, docs, and any architecture notes first.
- The top-level layout and entry points, to find the 3–7 major components and how they connect.
- The manifests (package.json, pom.xml, build files) for the tech list.
- `git -C <clone> log --reverse --format='%ad' --date=short | head -1` and the latest commit for the years, if the user didn't give them.
- Skim, don't trace. You're looking for: the problem, the components, the flows a user goes
  through, and the two or three design decisions that make the project interesting.

Keep the code-level findings to yourself. Most of them won't appear on the page. That's
the point of `style-guide.md` § Abstraction.

### 4. Ask follow-ups and save the brief

Ask Part 2 of the questionnaire: 2–4 questions specific to this project, drawn from what you
found (e.g. "Uploads write on a separate thread from reads — a deliberate performance
decision worth featuring?"). This is how you find out which implementation details are
major enough to mention. Wait for the answers.

Then write `src/content/projects/<slug>/brief.md` with every answer from both parts,
verbatim where possible. This file is committed and is what future regenerations start
from, so it must not contain anything the user marked confidential (confidential items stay
in the conversation only). The build ignores it.

### 5. Propose the outline, then stop

Present the outline in chat, not as a file:

- The frontmatter, filled in (see `format.md`). Map tech to the keys in
  `src/types/TechTypes.ts`. If a technology isn't there, say so. Adding it needs a badge
  color the user should pick.
- Every `##` section and `###` sub-heading, each with a one-line note of what it covers.
- Where each block goes (`:::terms`, `:::steps`, a banner, a diagram), with a line on why.
- Whether there's a case study.

Choose the structure per `style-guide.md` § Structure. Then **stop and ask for approval**.
The outline is where the level of abstraction gets decided, and it's much cheaper to
change here than after drafting.

### 6. Draft

Write `index.md` (and `case-study.md` if agreed) with `draft: true` in the frontmatter, so
it shows in dev and never in production. Follow the approved outline. If you need to
deviate, say so in step 8.

### 7. Critic pass

1. Run `npm run lint:content -- <slug> --forbid "<names from brief question 9>"`.
   Errors must be fixed. Treat each warning as a prompt: rewrite it, or keep it only if
   the style guide's exception applies, and note why in step 8.
2. Review the draft against the checklist at the end of `style-guide.md`. If you can launch
   a subagent, have a fresh one do this review. It won't share your attachment to the draft.
   Give it the style guide, the draft and the reference write-ups, and ask for violations
   only. Fix what it finds.
3. Run `npx vitest run src/content src/constants` to confirm the page builds and its links
   and related projects resolve.

### 8. Hand over

Delete the temporary clone (`rm -rf "${TMPDIR:-/tmp}/write-project/<slug>"`). The brief
holds everything later regenerations need, and a regeneration clones again.

Tell the user:

- The page is at `http://localhost:3000/projects/<slug>` (`npm run dev`) while it's a draft.
- Any lint warnings you kept, and why.
- Any deviation from the outline.
- What's left for them: removing `draft: true` once they're happy, adding the project to
  `featuredPathnames` in `src/constants/project.ts` if it should be on the home page, and
  any new `techType` entries.

## Regenerating an existing project

The same pipeline applies. Start from `brief.md` and the current page, and keep anything the
user hand-edited unless they say otherwise. To replace one of the old TSX projects
(PropMange, Chip8), write the new folder, remove the TSX file and its `addProject` line from
`src/constants/project.ts`, and keep the project's name so its URL doesn't change.
